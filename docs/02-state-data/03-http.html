03 · HTTP tipado y httpResource

Pedir datos a una API sin any, modelar carga y error, y elegir entre HttpClient con Observables o httpResource con signals.

  • Proyecto: ch02-03-http
  • Ruta: chapters/02-state-data/03-http
  • Requiere: 02-02-services-di

Arranca: ng serve ch02-03-http localhost:4200

Objetivo de la clase

provideHttpClient, HttpClient tipado y manejo de errores. Como extra, httpResource, estable desde Angular 22.

1. Configurar el cliente

// app.config.ts
import { provideHttpClient, withFetch } from '@angular/common/http';

export const appConfig: ApplicationConfig = {
  providers: [provideBrowserGlobalErrorListeners(), provideRouter(routes), provideHttpClient(withFetch())],
};

Sin provideHttpClient() cualquier inject(HttpClient) falla en runtime. withFetch() usa la Fetch API en vez de XMLHttpRequest.

2. Un servicio tipado

export interface Usuario {
  id: number;
  nombre: string;
  email: string;
}

@Service()
export class UsuariosService {
  private readonly http = inject(HttpClient);
  private readonly apiUrl = inject(API_URL);

  listar(): Observable<Usuario[]> {
    return this.http.get<Usuario[]>(`${this.apiUrl}/usuarios`);
  }

  detalle(id: number): Observable<Usuario> {
    return this.http.get<Usuario>(`${this.apiUrl}/usuarios/${id}`);
  }
}

El genérico de get<T> no valida nada: es una promesa de tipos, no un parser. Si la API devuelve otra forma, TypeScript no se enterará. Valida en el borde si el dato es crítico.

3. Errores

import { catchError, throwError } from 'rxjs';
import { HttpErrorResponse } from '@angular/common/http';

listar(): Observable<Usuario[]> {
  return this.http.get<Usuario[]>(`${this.apiUrl}/usuarios`).pipe(
    catchError((error: HttpErrorResponse) =>
      throwError(() => new Error(`No se pudo cargar la lista (${error.status})`)),
    ),
  );
}

HttpClient emite error para cualquier estado fuera de 2xx (y para fallos de red, donde status es 0). El componente no debería conocer HttpErrorResponse: tradúcelo en el servicio.

4. httpResource: la vía reactiva

En lugar de suscribirte, describes la petición como una función de signals. Cambia el signal de entrada y la petición se relanza. 

import { httpResource } from '@angular/common/http';

readonly usuarioId = signal(1);

readonly usuario = httpResource<Usuario>(
  () => `${this.apiUrl}/usuarios/${this.usuarioId()}`,
);
@if (usuario.isLoading()) {
  <app-spinner />
} @else if (usuario.error()) {
  <p>No se pudo cargar.</p>
} @else if (usuario.value(); as u) {
  <h2>{{ u.nombre }}</h2>
}
Señal Qué da
value() Último valor válido o undefined.
status() idle · loading · error · reloading…
isLoading(), error() Atajos para la plantilla.
reload() Fuerza otra petición con los mismos parámetros.

Para peticiones con estado complejo o que necesitan switchMap, sigue teniendo sentido RxJS. Para «pinta esto de la API», httpResource ahorra mucho código.

5. Interceptores funcionales

export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthService).token();
  return token ? next(req.clone({ setHeaders: { Authorization: `Bearer ${token}` } })) : next(req);
};
provideHttpClient(withFetch(), withInterceptors([authInterceptor]));

Un interceptor es una función, no una clase. Se registra una vez y afecta a todas las peticiones del inyector.

6. Ejercicio

  1. Configura provideHttpClient(withFetch()) y crea UsuariosService con listar() y detalle(id) tipados.
  2. Consume la lista con httpResource y pinta los tres estados: cargando, error y datos.
  3. Añade un buscador por id que use signal() como parámetro de httpResource y comprueba que cada cambio relanza la petición.
  4. Fuerza un error (URL inválida) y verifica que la UI lo muestra sin romper el componente.
  5. Repite la lista con HttpClient + toSignal() y compara: ¿qué versión tiene menos código?

Checklist de cierre

  • Build y prettier limpios.
  • Ningún any en las respuestas HTTP.
  • Los estados de carga y error están cubiertos en la plantilla.
  • Las URLs vienen de un InjectionToken, no están hardcodeadas en el componente.
