02 · Servicios e inyección de dependencias

Sacar estado y lógica del componente: un servicio singleton con signals y consumidores que lo piden con inject().

  • Proyecto: ch02-02-services-di
  • Ruta: chapters/02-state-data/02-services-di
  • Requiere: 02-01-signals
Objetivo de la clase

@Service, inject() y providedIn: 'root'. Entender qué significa singleton, cuándo quieres una instancia por componente y cómo sustituir un provider.

1. Declarar un servicio

Angular 22 trae el decorador @Service(): marca la clase y la deja disponible en el inyector automáticamente. 

import { Service, signal, computed } from '@angular/core';

@Service()
export class CarritoService {
  private readonly _lineas = signal<Linea[]>([]);

  readonly lineas = this._lineas.asReadonly();
  readonly total = computed(() =>
    this._lineas().reduce((suma, l) => suma + l.precio * l.cantidad, 0),
  );

  anadir(linea: Linea): void {
    this._lineas.update((previas) => [...previas, linea]);
  }
}

El equivalente tradicional, que también es válido, es @Injectable({ providedIn: 'root' }). Lo importante: el servicio expone asReadonly(), no el signal escribible. Los consumidores leen, el servicio decide.

@Service() acepta { autoProvided: false } si no quieres auto-registro, y { factory: () => T } para construirlo a mano. Para el 95 % de los casos, @Service() a secas.

2. Consumir con inject()

import { Component, inject } from '@angular/core';

@Component({
  selector: 'app-carrito',
  template: `<p>{{ carrito.total() | currency: 'EUR' }}</p>`,
})
export class Carrito {
  protected readonly carrito = inject(CarritoService);
}

Sin constructores. inject() solo funciona en contexto de inyección: campo de clase, constructor o una función que se ejecute ahí. No dentro de un setTimeout ni de un callback.

3. Jerarquía de inyectores

Dónde se declara Alcance
providedIn: 'root' / @Service() Uno para toda la app.
providers de un componente Una instancia por instancia de ese componente (y sus hijos).
providers de una ruta (loadChildren) Una instancia por ruta cargada. 
@Component({
  selector: 'app-editor',
  providers: [BorradorService], // instancia local, se destruye con el componente
  /* ... */
})
export class Editor {
  private readonly borrador = inject(BorradorService);
}

Si dos componentes piden un servicio cuyo estado esperas compartir y no se ven entre sí, mira quién lo declara en providers. Un servicio «duplicado» casi siempre es un provider local de más.

4. Inyección por token

Para valores de configuración o interfaces, se inyecta un token, no una clase.

export const API_URL = new InjectionToken<string>('API_URL');

// app.config.ts
providers: [{ provide: API_URL, useValue: 'https://api.ejemplo.dev' }];

// servicio
private readonly apiUrl = inject(API_URL);

Ventaja: en tests se cambia el valor sin tocar el servicio. { provide: API_URL, useValue: 'http://localhost:3000' } y listo.

5. Sustituir un provider

// app.config.ts
export const appConfig: ApplicationConfig = {
  providers: [
    { provide: CarritoService, useClass: CarritoConDescuentoService },
    // o useExisting / useValue según el caso
  ],
};

Es el mecanismo detrás de los dobles de test y de las implementaciones por plataforma (navegador / servidor en SSR).

6. Ejercicio

  1. Crea CarritoService con @Service(): lineas privadas, lectura con asReadonly(), total con computed().
  2. Crea dos componentes hermanos que inyecten el servicio: uno añade productos, otro muestra el total. Comprueba que comparten estado.
  3. Añade un componente con providers: [CarritoService] y explica por qué su total ya no coincide.
  4. Sustituye la URL por un InjectionToken y cámbiala en app.config.ts.
  5. Ordena el código: el componente no importa nada de HTTP, solo habla con el servicio.

Checklist de cierre

  • Build y prettier limpios.
  • Cero inyección por constructor: todo inject().
  • El estado de negocio vive en el servicio, no en el componente.
  • Los signals privados no se exponen escribibles.
