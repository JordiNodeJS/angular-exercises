01 · HTTP con cancelación: el caso donde RxJS sigue ganando

Un buscador que dispara una petición por tecla es el ejemplo de manual: la petición anterior ya no sirve y hay que cancelarla. Eso lo hace switchMap, no un signal.

  • Proyecto: ch05-01-http-cancel
  • Ruta: chapters/05-async-streams/01-http-cancel
  • Requiere: 02-03-http y 02-04-rxjs

Arranca: ng serve ch05-01-http-cancel localhost:4200

Objetivo de la clase

debounceTime, distinctUntilChanged, switchMap y takeUntilDestroyed. Al terminar sabes por qué una búsqueda reactiva no se resuelve con computed() ni con un effect().

1. El problema

Escribes «a», «ab», «abc» en tres decimas de segundo. Sin cancelación salen tres peticiones y la última en responder puede ser la de «a»: la interfaz muestra un resultado que no corresponde a lo que hay en el input.

Con un signal suelto no tienes forma de cancelar la petición anterior. Necesitas un stream.

2. La cadena completa

import { toSignal } from '@angular/core/rxjs-interop';
import { debounceTime, distinctUntilChanged, switchMap } from 'rxjs';

readonly resultados = toSignal(
  this.busqueda.valueChanges.pipe(
    debounceTime(300),
    distinctUntilChanged(),
    switchMap((texto) => this.http.get<Resultado[]>('/api/buscar', { params: { q: texto } })),
  ),
  { initialValue: [] as Resultado[] },
);

Cada operador resuelve una parte:

Operador Sin él
debounceTime(300) Una petición por tecla.
distinctUntilChanged() Repite la búsqueda si borras y vuelves a escribir lo mismo.
switchMap Respuestas fuera de orden: gana la última en llegar, no la última pedida.

switchMap cancela la petición anterior de verdad: HttpClient usa AbortController por debajo, así que la petición se aborta en el navegador. No es solo descartar la respuesta.

3. switchMap frente a sus hermanos

Operador Qué hace con el stream anterior Cuándo
switchMap Lo cancela. Búsquedas, autocomplete, navegar a un detalle.
mergeMap Lo deja correr. Eventos independientes que sí quieres todos (analytics).
concatMap Lo encola. Orden estricto, por ejemplo guardar en secuencia.
exhaustMap Ignora los nuevos mientras trabaja. Botón de guardar: un clic por operación.

4. Errores y reintentos

import { catchError, of, retry, timer } from 'rxjs';

this.http.get<Usuario>('/api/usuario').pipe(
  retry({ count: 2, delay: 1000 }),
  catchError(() => of(this.usuarioPorDefecto)),
);

retry vuelve a suscribirse al mismo Observable. Ojo: reintenta también los errores de negocio (404, 403), que no van a cambiar. Para eso, filtra por código antes.

5. Cancelar al destruir el componente

toSignal() ya se desuscribe al destruir el componente. Si te suscribes a mano: 

import { takeUntilDestroyed } from '@angular/core/rxjs-interop';

constructor() {
  this.estado$.pipe(takeUntilDestroyed()).subscribe((estado) => this.estado.set(estado));
}

Un .subscribe() sin takeUntilDestroyed sigue vivo después de navegar a otra ruta. Es la fuga más común en apps con streams.

6. Ejercicio

  1. Monta un buscador con debounceTime(300) y switchMap contra una API pública (por ejemplo api.github.com/search/users).
  2. Añade distinctUntilChanged() y comprueba que no repite la búsqueda al borrar y reescribir.
  3. Muestra un estado «buscando…» mientras llega la respuesta y «sin resultados» si llega vacía.
  4. Cambia switchMap por concatMap y escribe rápido: explica qué ves y por qué.
  5. Provoca un error (URL mal formada) y resuélvelo con retry + catchError.

Checklist de cierre

  • Build y prettier limpios.
  • La búsqueda cancela la petición anterior al escribir más rápido que la red.
  • Ninguna suscripción manual sin takeUntilDestroyed.
  • Sabes explicar por qué computed() no sirve para esto.
