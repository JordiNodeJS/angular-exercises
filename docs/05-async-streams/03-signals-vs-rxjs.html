03 · Signals y RxJS: dos modelos, no una moda

Los signals resuelven el estado síncrono de la vista y por eso desplazaron a RxJS en el día a día. Pero RxJS sigue siendo la herramienta para el tiempo: eventos, cancelación y flujos que empujan.

  • Requiere: 02-01-signals y 02-04-rxjs

Objetivo de la clase

Una regla de decisión clara, el puente entre los dos mundos (toSignal / toObservable) y los errores que se repiten al mezclar ambos modelos.

1. Dos formas de pensar

Signals RxJS
Tiras del valor: lo lees cuando lo necesitas. El valor te empuja: te enteras cuando cambia.
El estado es el centro. El flujo de eventos es el centro.
Derivar es Computed. Transformar es un operador.
No hay cancelación. Cancelar es una operación más.
Perfecto para la vista. Perfecto para el tiempo.

2. La regla de decisión

Situación Herramienta
Estado de la vista (contador, formulario, tildes) signal() / computed()
Un dato de API que se pinta tal cual httpResource() o toSignal()
Eventos rápidos y repetidos (input, scroll, resize) RxJS: debounceTime, switchMap
Peticiones que deben cancelarse RxJS con switchMap
Conexiones persistentes (WebSocket, SSE) RxJS con Subject y limpieza manual
Compartir estado entre componentes Servicio con signals privados y lectura asReadonly()

3. El puente: toSignal y toObservable

La frontera normal es: RxJS dentro del servicio, signals en el componente.

import { toSignal } from '@angular/core/rxjs-interop';

readonly usuarios = toSignal(this.usuariosService.listar(), {
  initialValue: [] as Usuario[],
});

En sentido contrario, cuando un operador tiene que reaccionar a un signal:

import { toObservable } from '@angular/core/rxjs-interop';

readonly busqueda = signal('');

readonly resultados = toObservable(this.busqueda).pipe(
  debounceTime(300),
  distinctUntilChanged(),
  switchMap((texto) => this.http.get<Resultado[]>('/api/buscar', { params: { q: texto } })),
);

toSignal() se desuscribe al destruir el contexto de inyección. Es la razón por la que no necesitas takeUntilDestroyed cuando trabajas en el borde.

4. Tres formas de traer datos de API

Forma Cuándo Coste
httpResource() Un recurso reactivo ligado a un signal de entrada. Código mínimo; estado de carga y error incluidos.
toSignal(http.get(...)) Una petición puntual al arrancar. Un signal; sin estado de recarga.
resource() Datos asíncronos con async propio. Más control; necesitas un loader.

5. Errores al mezclar

  • Un effect() que escribe otro signal. Casi siempre es un computed().
  • Pasar a signal demasiado pronto. Si conviertes la búsqueda a toSignal antes del debounceTime, pierdes la cancelación.
  • subscribe() sin limpieza. En el borde usa toSignal; si no, takeUntilDestroyed.
  • RxJS para estado síncrono. Un BehaviorSubject para un contador es más código que un signal y peor rendimiento.

6. Ejercicio

  1. Crea un contador con signal() y computed(). Sin RxJS.
  2. Añade un buscador con toObservable, debounceTime y switchMap, y trae el resultado a un signal con toSignal.
  3. Haz la misma petición con httpResource y compara el código y los estados de carga.
  4. Escribe un effect() que solo haga logging. Comprueba que no necesita escribir ningún signal.
  5. Decide en un párrafo qué herramienta usarías para un chat en vivo y por qué.

Checklist de cierre

  • Build y prettier limpios.
  • Sin subscribe() sin takeUntilDestroyed ni toSignal.
  • Los effect() no escriben signals.
  • Sabes justificar la elección entre signal y RxJS en cada caso del ejercicio.
