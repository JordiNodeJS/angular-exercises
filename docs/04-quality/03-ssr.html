03 · SSR e hidratación

HTML renderizado en el servidor y una app que despierta en el navegador sin repintar todo. Más prerender para lo estático.

  • Proyecto: ch04-03-ssr
  • Ruta: chapters/04-quality/03-ssr
  • Requiere: capítulo 03
Objetivo de la clase

@angular/ssr e hidratación. Entender cuándo SSR ayuda, cuándo estorba y qué código rompe en el servidor.

1. Añadir SSR

ng add @angular/ssr

Añade dependencias (@angular/ssr), server.ts, la configuración de servidor y los targets nuevos en angular.json. Como es una dependencia nueva, en este repo se pide antes de instalarla.

Para un proyecto desde cero también existe ng generate application --ssr. Aquí no se usa ng new: el workspace ya existe.

2. Modos de renderizado

RenderMode Qué produce
Server HTML por petición en el servidor. Datos por usuario.
Prerender HTML en build. Páginas iguales para todos (SSG).
Client CSR clásico. SPA detrás de login, por ejemplo. 
// app.routes.server.ts
import { RenderMode, ServerRoute } from '@angular/ssr';

export const serverRoutes: ServerRoute[] = [
  { path: '', renderMode: RenderMode.Prerender },
  { path: 'productos/:id', renderMode: RenderMode.Prerender },
  { path: 'cuenta/**', renderMode: RenderMode.Client },
  { path: '**', renderMode: RenderMode.Server },
];

La configuración se enchufa con provideServerRendering(withRoutes(serverRoutes)) en app.config.server.ts.

3. Hidratación

// app.config.ts
import { provideClientHydration, withEventReplay } from '@angular/platform-browser';

providers: [
  provideBrowserGlobalErrorListeners(),
  provideRouter(routes),
  provideClientHydration(withEventReplay()),
];

El HTML del servidor se reutiliza en el navegador en vez de regenerarse. Con withEventReplay() los clics hechos antes de que la app hidrate no se pierden.

Si el HTML del servidor no coincide con el del cliente, Angular avisa de un hydration mismatch y repinta. Casi siempre es contenido que depende de Date.now(), Math.random(), localStorage o window.

4. Código que rompe en el servidor

Problema Solución
window, document, navigator inject(DOCUMENT) o ejecutar en afterNextRender().
localStorage en el constructor Mover a afterNextRender() o a un servicio por plataforma.
@if (isPlatformBrowser()) en plantilla CSR y servidor pintan distinto: mismatch. Mantén el HTML igual.
Peticiones duplicadas HttpClient ya transfiere la caché del servidor al cliente; no la desactives sin motivo. 
import { Component, ElementRef, afterNextRender, viewChild } from '@angular/core';

export class Panel {
  private readonly caja = viewChild.required<ElementRef<HTMLElement>>('caja');

  constructor() {
    afterNextRender(() => {
      // solo navegador
      this.caja().nativeElement.scrollIntoView();
    });
  }
}

5. ¿Cuándo no usar SSR?

  • App interna detrás de login: no hay SEO que ganar y añades un servidor que mantener.
  • Todo el contenido depende del usuario: la parte útil no se puede prerenderizar.
  • No hay dónde ejecutar Node: usa outputMode: "static" y sirve ficheros.
"build": {
  "options": { "outputMode": "static" }
}

6. Ejercicio

  1. Añade SSR al ejercicio. Verifica con curl http://localhost:4000 que el HTML inicial ya trae contenido (no un <app-root> vacío).
  2. Configura app.routes.server.ts con una ruta Prerender y comprueba en dist/ que genera un .html estático.
  3. Añade provideClientHydration(withEventReplay()) y mira en el HTML la marca de hidratación y el comentario de <!--ngh-->.
  4. Pinta Date.now() en la plantilla y provoca un mismatch a propósito. Lee el warning entero.
  5. Sustituye el acceso a window por afterNextRender() y comprueba que el aviso desaparece.

Checklist de cierre

  • El build de SSR y el de navegador terminan sin errores.
  • El HTML servido incluye contenido renderizado en servidor.
  • Sin accesos directos a window / document en constructores.
  • Build y prettier limpios; dependencias nuevas justificadas.
